# Personnel leave report

The report page (`leavereport`) presents two data sources: period totals imported from the personnel leave workbook, and leave requests already recorded in the application. The import is a snapshot through the end of the reported month; it does not contain request-by-request history.

## Storage and import

Apply `php/migrations/2026_10_15_personnel_leave_snapshots.sql` once, then run the private phpMyAdmin import file created for the provided workbook. The import file contains personal employee data and is intentionally excluded from Git. It imports the 1405/06 snapshot and links a row to `users.id` only when the exact full name is unique in `users`. Duplicate personnel codes are not sufficient for linking. Unmatched and ambiguous rows remain available in the aggregate report by their imported name and code.

The workbook provides monthly and yearly used durations/counts and remaining durations. Duration values are stored as signed minutes. The displayed “allowed” duration is derived as `used + remaining` because the workbook has no separate allowed column. Negative balances are retained. The import does not overwrite leave settings or balances used by the live request workflow.

## API and permissions

`GET /api/admin/personnel-leave-report` returns available periods and rows. Add `year`, `month`, and `snapshot_id` to return the selected employee and applicable request history. The endpoint checks `role_perms` for the `leavereport` view key, matching the panel role permission control. Request history is read from the existing `requests` table and is available only when an imported row has an unambiguous `user_id` link.

The JSX source is `php/tools/panel_source.jsx`; `php/app/assets/panel.bundle.js` is generated by `php/tools/build_panel_bundle.sh` and must be rebuilt after source changes.
