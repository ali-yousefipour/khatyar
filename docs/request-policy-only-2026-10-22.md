# منبع یکتای تنظیمات درخواست‌ها — ۲۰۲۶/۱۰/۲۲

درخواست مالک: حذف و بی‌اثرکردن تنظیمات عمومی درخواست‌ها و استفادهٔ انحصاری از سیاست کاری.

## رفتار

- مسیرهای ثبت شخصی/مدیریتی و تأیید کارتابل/ادمین در `php/lib/routes.php` از همان guard مشترک استفاده می‌کنند. نبود سیاست تخصیص‌یافته و فعال، ثبت یا تأیید را با خطای روشن ۴۲۲ متوقف می‌کند؛ هیچ سقف عمومی یا سیاست پیش‌فرضی به‌صورت ضمنی جایگزین نمی‌شود. رد/لغو درخواست قبلی، حذف مدیریتی و مجوزهای موجود مستقل از سهمیه حفظ شده‌اند.
- سقف تعداد، مدت، حداقل/حداکثر و مهلت ثبت و تأیید از config سیاست کاری همان متقاضی می‌آیند. بلوک کنترل سقف‌های عمومی از مسیر ثبت حذف شد.
- گزینه‌های درخواست در `config.request_options` سیاست ذخیره می‌شوند: `approval_mode` (پیش‌فرض همان سلسله‌مراتب سازمانی)، `approver_id` برای مسئول مشخص، `manual_attendance_selfie`، `leave_require_substitute` و `request_sms_notify`. گزینه‌های بولیِ تعریف‌نشده false هستند؛ مقدار عمومی قبلی خوانده نمی‌شود. مسئول مشخص هنگام استفاده باید کاربر فعال معتبر باشد. سرویس عمومی پیامک همچنان باید فعال باشد؛ این تنظیم سرویس زیرساختی است، نه سهمیهٔ درخواست.
- پاسخ `/api/my/app-config` الزام جایگزین را از سیاست کاربر می‌خواند؛ نبود سیاست، سایر قابلیت‌های اپ را مسدود نمی‌کند.
- پاسخ ماندهٔ شخصی، مدیریتی و مودال تأیید، از `_req_policy_balance` استفاده می‌کند و `source=work_policy`، شناسه و عنوان سیاست را برمی‌گرداند. بدون سیاست فعال، ماندهٔ نامحدود ساختگی نمایش داده نمی‌شود و API خطای ۴۲۲ می‌دهد.
- مانده با همان قرارداد اعتبارسنجی محاسبه می‌شود: بازهٔ واقعی شمسی، توزیع مرخصی چندماهه در ماه‌های مربوط، حذف رکوردهای تکراری و تجمیع مدت روزانه/ساعتی. یک روز مطابق قرارداد موجود ۴۸۰ دقیقه است. `annual_daily` و `annual_hourly` دو نمایش معادل از سهمیهٔ مدت مشترک هستند؛ سقف تعداد درخواستِ هر حالت در فیلدهای `cap_count_*` جدا می‌ماند و به روز تبدیل نمی‌شود. allow_over فقط برای annual و طبق همان شرط اعتبارسنجی اعمال می‌شود.
- گزارش رسمی واردشدهٔ مرخصی (`official_snapshot`) به‌عنوان دادهٔ تاریخی مستقل حفظ می‌شود؛ مبنای سقف جدید نیست و بازنویسی نمی‌شود.
- کارت «تنظیمات درخواست‌ها (مرخصی/ماموریت/اضافه‌کار)» و کامپوننت RequestSettings از تنظیمات سایت و ایندکس جستجو حذف شدند. تنظیمات اکنون ۴۹ بخش دارد. گزینه‌های گردش تأیید/الزام‌ها در ویرایش سیاست کاری قرار دارند و ویرایش سیاست قدیمی بدون request_options، شاخهٔ JSON را ایمن می‌سازد.
- داده‌های قبلی app_settings، سوابق درخواست، کاربران و تخصیص سیاست‌ها حذف یا مهاجرت حدسی نشده‌اند. کلیدهای عمومی سابق از مسیر فعال خوانده نمی‌شوند. مدیر باید سیاست و تخصیص کاربر را صریح تنظیم کند.

## فایل‌ها و بررسی

منطق سرور در `php/lib/routes.php`، رابط در `php/tools/panel_source.jsx`، خروجی رسمی `php/app/assets/panel.bundle.js` و cache-key در `php/app/panel.html` تغییر می‌کنند. نسخهٔ محصول و schema ثابت هستند. workflow یکپارچگی، آزمون UI جدید سیاست را نیز اجرا می‌کند.

آزمون PHP درخواست‌ها برای نبود سیاست، عدم fallback عمومی، سهمیهٔ مشترک روزانه/ساعتی، سقف تعداد، allow_over و مرز ماه گسترش یافت. آزمون UI، حذف ویرایشگر عمومی و ایجاد گزینه‌های تودرتو در سیاست قدیمی و حفظ سقف‌های قبلی را بررسی می‌کند. آزمون تنظیمات با شمارش ۴۹ بخش هماهنگ شد. build رسمی و syntax و آزمون‌های مرتبط قبل از commit اجرا می‌شوند؛ نتیجهٔ workflow و تطبیق HTTP جدا گزارش می‌شود. عملیات واقعی ثبت/تأیید/رد روی دادهٔ تولیدی برای QA انجام نمی‌شود.
