# سنوات نیروها

## دامنه و مسیر واقعی اجرا

این قابلیت، **مدیریت تعداد روز سنوات** است؛ محاسبه مبلغ ریالی یا تغییر فرمول حقوق و مزایا نیست. نسخه برنامه تغییر نمی‌کند.

- منوی سایت: منابع انسانی ← سنوات نیروها؛ کلید مجوز `seniority` در `RolePerms` و `VIEWS`.
- منبع پنل: `php/tools/panel_source.jsx`، کامپوننت `PersonnelSeniority`.
- خروجی مرورگر: `php/app/assets/panel.bundle.js` که `php/app/panel.html` بارگذاری می‌کند.
- APIهای احراز هویت‌شده و مدیریتی:
  - `GET /api/admin/seniority`: همه نیروها، مبنا، اصلاح دستی، مجموع ماه‌ها و سنوات کل.
  - `PUT /api/admin/seniority/{id}`: ثبت مبنا یا اصلاح عدد نهایی با دلیل و `revision`.
  - `POST /api/admin/seniority/{id}/recalculate`: محاسبه فقط ماه جاری سرور؛ بدنه `{"period":"1405-07"}`.
  - `GET /api/admin/seniority/{id}/history`: حداکثر ۲۰۰ رویداد آخر شخص.
- پیاده‌سازی: `php/lib/Seniority.php`؛ ثبت routeها در `php/lib/routes.php`.
- منبع غیبت: همان `_attendance_report(userId, from, to)` و فیلد `days[].absent` گزارش تردد. موتور حضور، GPS، شیفت، تعطیلی و درخواست‌های تأییدشده تغییر نکرده‌اند.
- تقویم: طول ماه از `IranCalendar::monthLength`؛ تاریخ جاری در منطقه زمانی `Asia/Tehran`.

## اطلاعات مبنا و فایل دریافتی

فایل ورودی یک شیت با ۱۰۷ ردیف شماره‌دار دارد: **۱۰۲ نفر با شناسه و ۵ ردیف کاملاً خالی با سنوات صفر**. مجموع روزهای ثبت‌شده ۲۲۰٬۳۱۴ است. داده‌ها تا **۱۴۰۵/۰۶/۳۱** پوشش دارند.

SHA256 فایل اصلی: `98d180ab2ec326842d84184f2fd5b5ce386d2d0bde25876bc89196deddbf801e`.

کد ملیِ عددی به رشته ۱۰ رقمی با صفر ابتدای لازم تبدیل می‌شود؛ فقط خطای اعشاری کوچک‌تر از `0.000001` در روزها گرد می‌شود. روز واقعاً کسری، منفی، نامعتبر و شناسه تکراری رد می‌شوند. نام و کد ملی افراد در این مستند یا Git ثبت نمی‌شوند.

## مدل ذخیره‌سازی

Migration عمومی: `php/db/seniority_schema.sql`؛ API نیز جدول‌ها را پیش از استفاده با `CREATE TABLE IF NOT EXISTS` آماده می‌کند.

1. `personnel_seniority`: یک ردیف مبنا برای هر `user_id`؛ `base_days`، `base_through_jdate`، `adjustment_days`، منبع، بازبینی و زمان تغییر.
2. `personnel_seniority_months`: یک ردیف برای هر شخص/سال/ماه، با کلید اصلی `(user_id,jyear,jmonth)`؛ تعداد روزهای واجد محاسبه، غیبت، روزهای منظورشده، تاریخ غیبت و آخرین روز بررسی‌شده.
3. `personnel_seniority_history`: تاریخچه ثبت مبنا، ورود اکسل، اصلاح دستی و محاسبه؛ جمع قبل، بعد، اختلاف، دلیل و عامل تغییر.

فیلد «میزان سنوات شخص (روز)» از رابطه زیر به دست می‌آید؛ در `users` یک کپی قابل واگرایی از جمع نگهداری نمی‌شود:

```text
seniority_days = base_days + adjustment_days + SUM(monthly.credited_days)
credited_days = eligible_calendar_days - completed_absent_days
```

## به‌روزرسانی ماهانه و جلوگیری از تکرار

طبق انتخاب کارفرما، **تمام روزهای ماه، از جمله روزهای آینده، منهای غیبت** منظور می‌شود؛ این مقدار تا پایان ماه علی‌الحساب است. غیبت روز جاریِ هنوز پایان‌نیافته و روزهای آینده از نبود تردد استنباط نمی‌شود. غیبتِ گزارش تردد فقط برای روزهای پایان‌یافته تا دیروز کسر می‌شود. تعطیلات، جمعه، روز آزاد و مرخصی/مأموریت تأییدشده طبق منطق موجود گزارش رفتار می‌کنند؛ کسری ساعت به غیبت تمام‌روز تبدیل نمی‌شود.

- روزهای تا تاریخ مبنا دوباره منظور نمی‌شوند؛ مبنای میان‌ماه فقط روزهای بعد از مبنا را واجد محاسبه می‌کند.
- سهم قبلی ماه **جایگزین** می‌شود؛ اختلاف جدید و قبلی می‌تواند صفر، مثبت یا منفی باشد. ماه‌های قبلی دست‌نخورده می‌مانند؛ محاسبه ماه‌های جاافتاده، بازپردازش گذشته یا زمان‌بندی خودکار در این قابلیت وجود ندارد.
- مثال: مبنا ۱۰۰ روز، ماه ۳۰ روز و ۲ غیبت ⇒ ۱۲۸ روز؛ اجرای مجدد ⇒ ۱۲۸؛ تبدیل یک غیبت به حضور ⇒ ۱۲۹؛ اضافه‌شدن یک غیبت ⇒ کاهش یک روز.
- محاسبه گروهی فقط روی نیروهای **فعال و دارای مبنا در فهرست فیلترشده** انجام می‌شود، نه فقط صفحه فعلی جدول. درخواست‌ها ترتیبی‌اند؛ شکست یک نفر بقیه را متوقف نمی‌کند و نام/دلیل شکست نمایش داده می‌شود.
- نیروهای بدون مبنا خودکار با صفر فرض نمی‌شوند. ورود SQL یا ثبت دستی مبنا لازم است. نیروی غیرفعال قابل گزارش و اصلاح دستی است، ولی خودکار سنوات ماه جاری نمی‌گیرد.
- `GET_LOCK` برای هر شخص در سطح دیتابیس مانع هم‌زمانی ورود، ویرایش و محاسبه API می‌شود؛ تراکنش، ledger و تاریخچه را اتمیک ذخیره می‌کند. Import دستی SQL را در زمان توقف عملیات و پس از backup اجرا کنید.
- گزارش ترددِ قدیمی قبل از تراکنش خوانده می‌شود، چون آماده‌سازی جدول‌ها و auto-close آن ممکن است DDL اجرا کند. شکست ذخیره تاریخچه، کل تغییر سنوات را rollback می‌کند.
- اصلاح دستی، مبنا و سهم ماه‌های ثبت‌شده را بازنویسی نمی‌کند؛ اختلافِ عدد نهایی در `adjustment_days` ذخیره می‌شود. `revision` مانع overwrite فرم قدیمی است. عدد منفی مجاز نیست؛ کاهش خودکار منجر به جمع منفی، با خطا متوقف می‌شود.

## ورود اکسل با phpMyAdmin

ابزار تولید SQL: `php/tools/prepare_seniority_import.py`؛ نیاز توسعه‌ای آن `openpyxl` است، نه وابستگی PHP سایت.

```powershell
python php/tools/prepare_seniority_import.py "مسیر فایل اکسل.xlsx" ".build-temp/seniority"
```

خروجی‌های خصوصی حاوی داده پرسنلی‌اند و **نباید commit یا روی مسیر عمومی سایت آپلود شوند**:

1. `seniority_1405_06_preview.sql`: صرفاً جدول‌های موقت و گزارش تطبیق؛ هیچ سنواتی را تغییر نمی‌دهد.
2. `seniority_1405_06_apply.sql`: شامل همان داده و کنترل تطبیق، migration، تراکنش ورود و گزارش نتیجه. فایل مستقل است و به زنده‌ماندن اتصال preview وابسته نیست.
3. `manual_mapping.tsv`: ردیف‌های بدون شناسه؛ در فایل دریافتی این پنج ردیف نام و نام خانوادگی هم ندارند و نباید برای آن‌ها شخص فرضی ساخته شود.

مراحل:

1. از پایگاه داده backup بگیرید و دیتابیس صحیح را در phpMyAdmin انتخاب کنید.
2. فایل preview را Import کنید؛ `matched`، `user_not_found`، `ambiguous_match`، `identity_conflict`، `duplicate_user_mapping` و `blank_source_row` را بررسی کنید.
3. فقط کد ملی یا شماره پرسنلی مبنای تطبیق است؛ تطبیق نام انجام نمی‌شود. تضاد شناسه‌ها، چند کاربر برای یک ردیف یا چند ردیف برای یک کاربر، خودکار درج نمی‌شوند. در صورت تأیید انسانی یک ردیف، آخرین مقدار `NULL` همان tuple را با `users.id` مورد تأیید جایگزین و preview را دوباره اجرا کنید؛ ردیف‌های واقعاً خالی را مپ نکنید.
4. پس از تأیید پیش‌نمایش، فایل apply را Import کنید. فقط وضعیت `matched` درج می‌شود و سنوات مبنا **۱۴۰۵/۰۶/۳۱** است. نتیجه آخر فایل نشان می‌دهد کدام ردیف وارد، قبلاً وارد یا به دلیل مبنای موجود حفظ شده است.
5. اجرای مجدد Import مبنا، اصلاح دستی یا ماه‌های محاسبه‌شده قبلی را بازنویسی نمی‌کند. برای اصلاح مبنای اشتباه از صفحه مدیریت و تاریخچه استفاده کنید، نه تغییر کورکورانه SQL.
6. صفحه سنوات را بازخوانی و جمع/تعداد تطبیق‌یافته را با گزارش SQL کنترل کنید؛ پیش از ورود کامل مبنا، دکمه ماهانه را اجرا نکنید.

این ابزار هیچ اتصال یا اجرای خودکار روی دیتابیس production ندارد. تعداد کاربران واقعاً تطبیق‌یافته فقط پس از اجرای preview روی دیتابیس مقصد مشخص می‌شود.

## رابط و گزارش

فیلتر نام/کد ملی/شماره پرسنلی با ارقام فارسی یا انگلیسی، سمت، منطقه، فعال/غیرفعال و وضعیت مبنا؛ جدول صفحه‌بندی‌شده، نمایش صفر در برابر «ثبت نشده»، ویرایش با دلیل، تاریخچه، خروجی Excel و چاپ. خروجی همه ردیف‌های فیلترشده را شامل می‌شود؛ کد ملی به‌صورت متن و با صفر ابتدایی حفظ می‌شود و سلول‌های متنی با پیشوند فرمول ایمن می‌شوند. عنوان و داده چاپ escape می‌شوند.

برای سمت‌هایی که فهرست مجوز منویشان صریحاً محدود شده است، در تنظیمات دسترسی نقش، `seniority` را فعال کنید؛ محدودیت قبلی خودکار دور زده نمی‌شود.

## ساخت، آزمون و استقرار

```bash
cd php
bash ./tools/build_panel_bundle.sh
node --check app/assets/panel.bundle.js
node tests/seniority_ui_test.cjs
php tests/seniority_test.php
python tests/seniority_import_test.py
```

آزمون‌های PHP از Db جعلی کنترل‌شده برای تراکنش/قفل و توابع واقعی تقویم/محاسبه استفاده می‌کنند؛ جای آزمون دیتابیس MySQL واقعی نیستند. آزمون UI کد تولیدی bundle را اجرا می‌کند. آزمون Import با ورودی مصنوعی، صفر اول، گردکردن، ردیف خالی، تکرار شناسه و عدم بازنویسی را بررسی می‌کند.

workflow رسمی `.github/workflows/deploy-php.yml`، کتابخانه محافظت‌شده `Seniority.php` را با installer توکن‌دار و کنترل SHA پیش از `routes.php` نصب می‌کند؛ درگاه FTP مستقیماً روی `lib/` مجوز نوشتن ندارد. فایل private SQL/اکسل جزو payload نیست. نتیجه تست محلی، workflow، checksum هاست و اجرای SQL روی دیتابیس، مراحل مستقل‌اند و نباید یکی را به‌جای دیگری موفق اعلام کرد.
