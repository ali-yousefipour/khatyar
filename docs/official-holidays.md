# مستندات ثبت تعطیلات رسمی

## هدف

این سند منطق، ساختار و خطاهای شناخته‌شده مربوط به ثبت و جایگزینی تعطیلات رسمی در سامانه خطیار را ثبت می‌کند تا در توسعه‌های بعدی دوباره مشکل ایجاد نشود.

## اجزای اصلی

- API: `php/app/api/admin-holiday-seed.php`
- رابط کاربری: `php/app/assets/official-holiday-seed-ui.js`
- منبع تعطیلات: `php/app/lib/IranCalendar.php`
- جدول پایگاه داده: `holidays`
- دکمه پنل در بخش «شیفت و کارکرد → تعطیلات رسمی» قرار دارد.

## تاریخچه اصلاحات مهم

### 1. احراز هویت مدیریتی

نسخه اولیه به ستون `users.is_admin` وابسته بود و در محیط عملیاتی با خطای زیر مواجه شد:

`Unknown column 'u.is_admin' in 'field list'`

احراز هویت سپس به‌صورت schema-safe پیاده‌سازی شد: ابتدا ستون‌های موجود در `users` و `roles` با `SHOW COLUMNS` بررسی می‌شوند و فقط ستون‌های موجود در query استفاده می‌شوند. دسترسی مدیریتی بر اساس فیلدهای مدیریتی موجود و عناوین نقش‌های مجاز بررسی می‌شود.

نکته: «سطح» نقش، معیار مستقیم دسترسی پنل نیست؛ سطح بیانگر ارشدیت است. بنابراین در تغییرات بعدی نباید صرفاً از شرطی مانند `roles.level >= 3` برای دسترسی این API استفاده شود.

### 2. منبع تعطیلات رسمی

تعطیلات رسمی از `IranCalendar::events($year)` دریافت می‌شوند و فقط رویدادهایی که `is_holiday` دارند وارد فهرست رسمی می‌شوند.

سال از `?year=` یا body دریافت می‌شود و اعداد فارسی/عربی نیز به انگلیسی تبدیل می‌شوند. بازه معتبر سال ۱۳۹۰ تا ۱۵۰۰ است؛ خارج از این بازه، سال جاری جلالی به‌صورت fallback محاسبه می‌شود.

### 3. سازگاری با جدول `holidays`

API ابتدا وجود جدول را تضمین می‌کند و در صورت نیاز ستون‌های پایه `jdate` و `title` را بررسی/ایجاد می‌کند. برای علامت‌گذاری تعطیلات رسمی، در صورت وجود/امکان ایجاد از `source` با مقدار `official` و `is_official` با مقدار `1` استفاده می‌شود.

به دلیل وجود دیتابیس‌های قدیمی، هرگز نباید فرض شود که تمام ستون‌های مدیریتی جدید در همه محیط‌ها وجود دارند.

### 4. خطای مهم Duplicate Entry

در یکی از نسخه‌های جایگزینی، ابتدا تعطیلات رسمی قبلی حذف و سپس همه تعطیلات رسمی دوباره `INSERT` می‌شدند. در محیط عملیاتی به علت وجود محدودیت یکتا روی `holidays.jdate`، API با خطای زیر مواجه شد:

`SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry '1405-01-01' for key 'holidays.jdate'`

علت این بود که ممکن بود رکورد همان تاریخ از قبل وجود داشته باشد و حذف قبلی آن به هر دلیل آن رکورد را پوشش نداده باشد.

**راه‌حل نهایی و الزامی:** قبل از `INSERT` برای هر تاریخ رسمی، رکورد موجود با هر دو قالب `YYYY-MM-DD` و `YYYY/MM/DD` بررسی شود. اگر رکورد وجود داشت، همان رکورد `UPDATE` شود و در صورت نبودن، `INSERT` انجام شود.

این رفتار باید حفظ شود؛ API باید idempotent باشد، یعنی اجرای چندباره آن نباید باعث خطای duplicate یا ایجاد رکورد تکراری شود.

### 5. عدم استفاده از Transaction در نسخه عملیاتی فعلی

در جریان رفع مشکل، نسخه‌ای که از transaction (`START TRANSACTION` / `COMMIT` / `ROLLBACK`) استفاده می‌کرد با رفتار قبلی سامانه سازگار نبود و خطاهای عملیاتی ایجاد کرد. نسخه پایدار به الگوی ساده و proven قبلی برگشت و transaction اجباری برای این endpoint استفاده نمی‌کند.

بنابراین در توسعه‌های بعدی، اضافه کردن transaction به این endpoint بدون بررسی کامل سازگاری `Db` و schema عملیاتی انجام نشود.

## رفتار صحیح API

در اجرای موفق باید پاسخ JSON مشابه زیر باشد:

```json
{
  "ok": true,
  "year": 1405,
  "total": 30,
  "inserted": 0,
  "updated": 0,
  "existing": 30
}
```

مقادیر واقعی `total`، `inserted`، `updated` و `existing` بر اساس دیتابیس تغییر می‌کنند.

در اجرای مجدد روی همان سال، طبیعی است که رکوردهای موجود شناسایی شوند و دیگر خطای duplicate رخ ندهد.

## خطایابی

API در صورت خطای داخلی باید `stage` و `detail` را نیز در JSON برگرداند. مراحل مهم عبارت‌اند از:

- `احراز هویت مدیریتی`
- `تعیین سال`
- `آماده‌سازی جدول تعطیلات`
- `دریافت تعطیلات رسمی سال ...`
- `بررسی YYYY-MM-DD`
- `درج تعطیلات رسمی جدید سال ...`

این اطلاعات برای تشخیص دقیق خطا در production ضروری هستند و نباید در تغییرات بعدی حذف شوند.

## قواعد مهم برای توسعه آینده

1. `admin-holiday-seed.php` باید **idempotent** باقی بماند.
2. قبل از هر `INSERT`، وجود رکورد همان `jdate` بررسی شود.
3. محدودیت یکتای `holidays.jdate` باید فرض شود.
4. قالب تاریخ را در مقایسه‌ها هم `YYYY-MM-DD` و هم `YYYY/MM/DD` در نظر بگیرید.
5. به وجود `users.is_admin` یا سایر ستون‌های جدید بدون بررسی schema اعتماد نکنید.
6. «سطح» نقش را با «دسترسی پنل» اشتباه نگیرید.
7. منبع رسمی تعطیلات `IranCalendar::events()` است؛ فهرست تعطیلات را در UI به‌صورت hard-code تکثیر نکنید.
8. تعطیلات رسمی باید با marker مناسب مانند `source=official` و/یا `is_official=1` قابل تشخیص باشند.
9. تعطیلات دستی کاربران نباید در فرآیند ثبت تعطیلات رسمی حذف شوند.
10. خطاهای API باید JSON معتبر، `stage` و `detail` داشته باشند تا خطایابی production ممکن باشد.
11. تغییر این endpoint باید با تست اجرای چندباره روی یک سال انجام شود.
12. بعد از تغییر API، حتماً نسخه موجود روی سرور با `main` مقایسه شود و cache مرورگر/asset نیز در صورت نیاز cache-bust شود.

## رابط کاربری

اسکریپت `official-holiday-seed-ui.js` دکمه «بررسی و اضافه نمودن تعطیلات رسمی» را دقیقاً داخل بخش تعطیلات رسمی در تب «شیفت و کارکرد» قرار می‌دهد. این دکمه نباید fallback به صفحه login، `body` یا `#root` داشته باشد؛ محل قرارگیری باید همان بخش تعطیلات رسمی باقی بماند.

رنگ دکمه در نسخه فعلی با رنگ سبز استفاده‌شده در طراحی سامانه تنظیم شده است.

## وضعیت فعلی

نسخه فعلی endpoint روی `main` باید مبنای توسعه‌های بعدی باشد. هر تغییر در منطق تعطیلات رسمی باید این سند را نیز به‌روزرسانی کند، مخصوصاً اگر schema جدول، روش احراز هویت، منبع تقویم، الگوریتم idempotency یا محل/رفتار دکمه تغییر کند.
